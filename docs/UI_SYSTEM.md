# UI system

## Direction

The public game name is **Sunmark**, pronounced **سان‌مارک** in Persian. `src/brand.ts` supplies the shared product name and description for runtime UI, tutorial welcome, and Vite/PWA metadata. The menu title renders Sunmark as an explicit LTR English text run inside the Persian RTL layout; the smaller eyebrow includes the Persian pronunciation. Keep names as runtime text. The preserved gold sun-rosette emblem remains the app mark.

The user chose a Phaser Graphics interface on 2026-10-13, superseding the earlier visible DOM/CSS HUD. The approved **carved-stone interface** uses limestone controls, basalt panels, honey-colored primary slabs, cut corners, broad chiseled bevels, recessed grooves, and restrained mineral grain. It develops the original royal-expedition direction after the user requested a more ancient, carved material feel. Stone is the only UI treatment. The previous lapis implementation and URL theme selector have been removed following user approval. The board remains the hero. See [PHASER_UI_DESIGN.md](PHASER_UI_DESIGN.md) for research and component decisions.

All visible UI surfaces are Phaser Graphics: menu frame, buttons, player chips, progress pips, resource trays/cards, construction cards, trade selectors, modal frames/backdrops, scroll indicators, and destination lists. Labels are Phaser Text using runtime Persian strings. Existing resource, ornament, bank, and victory art remains cropped Phaser Images. No Persian text is baked into assets and ownership color remains runtime data.

## Layout targets

- Mobile portrait first: 390 × 844 CSS pixels, centered maximum width 480. Device safe-area insets reduce the content region; the background extends behind them.
- The shell is fixed to the top of the viewport. A shared `--app-height` uses dynamic height in browser tabs, with a `100vh` fallback and a `100vh` override for standalone apps. Installed iOS apps with a translucent status bar can under-report dynamic/visual viewport height; do not subtract safe-area insets from the canvas or compensate with a device-specific offset. Match/menu controls retain their own safe-area padding; the footer's Phaser fill extends through the home-indicator inset. Dialog and portrait limits use the same shell height. The document fallback color matches the current stone footer. See [WebKit 254868](https://bugs.webkit.org/show_bug.cgi?id=254868) and [WebKit's safe-area guidance](https://webkit.org/blog/7929/designing-websites-for-iphone-x/).
- Standard rows: header 104, context 48, resources 60, dock 52, primary 52, bottom spacing 4 pixels. The header contains a 48-pixel personal row and a 48-pixel opponent scoreboard, with four pixels of gap and four of vertical padding. The HUD reserves 320 pixels, giving the board 524 pixels at the reference size without safe-area insets. On the 390 × 844 reference with 47/34-pixel iPhone safe insets, 443 pixels remain for the board (391 during placement), enough to retain the full 310-pixel-wide island and its ocean margin.
- Below 720 safe-content pixels, the resource hand becomes 56 pixels; the HUD reserves 316 pixels. All match buttons, including context/history and primary actions, retain 48-pixel touch heights. Compact sizing uses shared CSS row variables rather than separate button/typography overrides.
- Opening setup uses the same preview/confirmation controls and separate 52-pixel destination-list row as later placement. Initial pieces are labeled free, paid-build/trade workspaces remain unavailable, and the required road is anchored to the just-confirmed settlement. Unselected starting settlement sites use small intersection markers instead of dozens of full building previews. The first ordinary turn belongs to the highest opening roller; the header remains human-owned. See [OPENING_SETUP.md](OPENING_SETUP.md).
- Placement reserves a separate 52-pixel row for an in-game destination-list button. It never covers land or port markers. The list previews a legal target, closes, and leaves final confirmation on the main screen. Tile inspection also has an in-game list reached from Help. Native dropdowns are absent from the visible interface.
- One Phaser game, one full-shell canvas, three scenes: backdrop, inset board camera, full-shell interface. CSS and ResizeObserver measure the board region independently. `Scale.NONE` uses an explicitly sized backing buffer at device pixel density, capped at 3× and four million pixels for mobile fill rate. The canvas keeps the shell's CSS size; `rendering/displayGeometry.ts` and `display.ts` project CSS coordinates through physical camera viewports, leaving layouts and touch targets unchanged. Browser resize and resolution-media-query changes refresh density. The HUD is never scaled with the fitted board.
- `fitBoard()` fits the radius-two island (5√3 radii wide, 8 high) with 40 pixels of ocean clearance on every side, without a radius cap, zoom, or panning. At 390 × 524 the land remains approximately 310 × 286; on shorter screens and during placement, the additional board height prevents unnecessary shrinking. Width still limits the largest complete island, including its ports. RTL does not mirror geography.
- Buttons have explicit line heights rather than inheriting sheet paragraph leading. Dock and primary controls are 48 pixels high with shallow two-pixel stone feet contained within their measured bounds, one-pixel shadows, and restrained bevels. The X and three-dot controls draw a centered 32-pixel stone face and 20-pixel glyph within a 48 × 48 touch region. Keyboard focus outlines the full touch region. Sheet headers start at 60 pixels and grow for wrapped titles.
- The header’s personal row shows the fixed human’s name, stone-seal avatar, ownership color, score/target, tied-aware rank, and phase/round; tapping it opens personal details. Opponent turns name the acting bot and hide its dice. Three compact opponent cards show distinct avatars, names, an explicit «ربات» label, public score/target, progress pips, and a textual turn/leader indicator. Cards stay in seat order, with color and text marking the active seat, and open the public opponent detail sheet. Tied leaders share the same rank; finished games show the winning opponent without a false active-turn indicator. Exact opponent inventories never enter this projection. The resource hand remains human-owned.
- The hand keeps exact counts across the full card width in its upper row, with a 22-pixel resource icon (18 on narrow screens) and its name together below. This reduces vertical space without abbreviating counts or removing names. Resource costs use 26-pixel icons, placement costs 20, trade cards 28, and port controls 23. Atlas proportions are maintained through `--icon-size`; transforms and negative margins no longer alter layout.
- Detail rows wrap in two flexible columns; construction headers may wrap; trade controls use explicit line heights and narrow-screen padding. The menu centers safely when it fits and remains scrollable without losing its top on shorter screens.
- The nine 32-pixel port islets sit 20 pixels offshore, within the 40-pixel board margin. See [PORTS.md](PORTS.md).

## Rendering and input ownership

- `scenes/BackdropScene.ts` covers the menu with the preserved palace image and matches with a procedural ocean. `rendering/ProceduralOcean.ts` caches a bounded-resolution shader material at 30 Hz, with a generated Canvas/Graphics fallback; it pauses in menus, modal panels, hidden tabs, and reduced-motion mode. The original ocean PNG is a preserved reference, not a runtime download. See [GAME_BACKGROUND_PLAN.md](GAME_BACKGROUND_PLAN.md).
- `scenes/GameScene.ts` owns the inset board camera, terrain, coast, pieces, ports, previews, and board effects. Its camera size and semantic board surface share measurements. `rendering/boardInput.ts` listens to that surface and transforms client positions into camera-local coordinates.
- `ui/GameHud.ts` assembles **transparent semantic controls** and responsive layout nodes. These are the input/accessibility adapter: real buttons, labels, a live region, and a native modal dialog preserve keyboard navigation, screen-reader content, focus trapping, and scrolling. Their labels and state come from the local session. CSS opacity hides their visual output without removing semantics or hit areas. Name entry uses a transparent native input for Persian IME, autofill, and the phone keyboard. Its value is mirrored into an aria-hidden layout span; Phaser paints that measured runtime text, focus border, caret, and selection using browser text ranges. Name-sheet input DOM is preserved across unrelated platform updates to keep composition and selection intact. No visible input layer is added above the canvas.
- `ui/InterfaceScene.ts` paints the same layout as Graphics, Text, and preserved Image crops. The stage is pointer-transparent; semantic buttons dispatch through `GameHud` into the existing session. The canvas is decorative in the accessibility tree, preventing duplicate announcements.
- `ui/graphicsTheme.ts` supplies the limestone, honey, basalt, inset, card, and ivory materials. Chamfered polygon faces, upper-left lighting, broad facets, engraved double keylines, deterministic edge grain, shallow seams, and short tooling marks retain the approved stone treatment. Texture avoids the central label field and never consumes the game random source.
- `ui/headerModel.ts` projects public standings and computes a full-width header backdrop from canvas y=0 through the measured header bottom, filling top/side safe insets with the same stone material. Controls retain the match grid’s safe-area padding. `ui/playerIdentity.ts` supplies stable seat avatars, robot names, and bounded/normalized player names; `ui/playerAvatarArt.ts` draws original human/robot stone seals with runtime owner-colored rims, without bitmap downloads or brand artwork.
- `ui/graphicsComponents.ts` applies the materials to every control/card/panel, including pressed, disabled, selected, active-player, and keyboard-focus states. Selected choices have a contrasting bronze outline/rosette on light stone and warm gold on dark panels; focus has a separate outer ring. Victory progress derives from the core player summary and match target.
- `ui/semanticText.ts` measures browser-wrapped text by line so Phaser retains Persian shaping, bidi digits, inline labels, and responsive wrapping. Text crops honor overflow regions and texture resolution. `textGeometry.ts` computes baseline/reading-edge positions and ellipsizes constrained labels in logical reading order. The scrollable modal content uses a Phaser 4 external Mask filter in WebGL and a Graphics geometry mask in Canvas; the header and portrait stay outside it. Do not use `setMask()` for WebGL: Phaser 4 ignores that Canvas-only API.
- Repaint only after layout/content/focus/press/scroll changes. Stable Text/Image objects are reused, while removed semantic nodes release their objects. The observer excludes Phaser's own hidden RTL text canvases. Effects animate separately through bounded tweens.
- `ui/bottomSheet.ts` owns native modal semantics, close/Escape/backdrop handling, focus restoration, and independent content scrolling. Normal sheets may supply a fixed footer, painted outside the body mask, for trade summaries and confirmation actions. Its visible shell, shade, heading, controls, and scroll thumb are drawn in Phaser.
- `ui/sheets.ts` describes construction, bank/ports, player/tile/port details, history, help, target/inspection lists, results, and unfinished-trade warnings. `ui/components.ts` supplies escaped semantic markup and art identifiers.
- `ui/session.ts` owns the fixed human seat, confirmed state, guarded human/bot command entry points, open sheet, uncommitted trade/placement drafts, notices, latest transition, and the last 100 events. Confirmed state, history, and tutorial memory are persisted through the optional local MatchStore; no online projection is implied.
- `ui/botTurns.ts` paces independently validated bot commands every 650 ms, pausing ordinary turns for sheets, hidden pages, or updates, while allowing replies to human offers in the domestic sheet and cancelling stale state callbacks. No animation completion drives a rule command.
- `ui/GameFeedback.ts` consumes confirmed transitions once; `ui/GraphicsFeedback.ts` draws finite resource flights, delta labels, focus/confirmation emphasis, and victory sparkles/glint. `ui/motion.ts` shares live visibility/reduced-motion preferences. There are no visible DOM animation layers. See [ANIMATION_DESIGN.md](ANIMATION_DESIGN.md).
- `rendering/pieces.ts` retains orthographic Graphics settlement/city/road geometry and arbitrary ownership colors. The `?demo=pieces` page remains an isolated developer gallery, not part of the game UI. See [PIECE_RENDERING.md](PIECE_RENDERING.md).

## Interaction and language

- Persian RTL throughout; resource order is wood, brick, wheat, wool, stone in RTL reading order.
- Human status is fixed to this device’s controller, independent of active-player index. Help → وضعیت من retains the human’s building counts, resources total, and port access. The optional opponent sheet shows public score/building counts and who is acting, without exact opponent inventories.
- Default ownership colors remain blue `#438bff`, rose `#ff526e`, cyan `#26d4e8`, and violet `#c16bff`, supplied by `core/game.ts`. The renderer accepts arbitrary `Player.color` values.
- The persistent resource hand belongs to the human on this device. Exact counts, icons, and labels stay visible during bot turns. Bank/primary mutation controls are disabled until the human’s turn; construction stays inspectable with human-only costs and turn explanations; domestic offers/responses to the active bot are available after its roll/robber resolution; inspection, history, and help remain available and pause bot pacing through the native modal.
- The dock exposes Build and Trading; Trading has Player and Bank/Ports tabs. Domestic trading is available during any action phase, restricted to the acting opponent off-turn; bank/port controls remain human-turn-only. Negotiation uses recipient cards, paired resource counters, per-offer statuses/counters, and a separate final confirmation with human balance preview and receipt. All bundles consistently say what the human gives and receives. See [DOMESTIC_TRADING.md](DOMESTIC_TRADING.md). Before a roll or required robber relocation, sheets remain inspectable and explain unavailability. Development cards, turn timers, and online controls are absent.
- Construction shows core-derived costs, explicit shortages, built counts, and legal targets. Supplies remain unlimited. Choose a type, preview a highlighted target or use the list, then confirm. Cancellation pays nothing.
- Robber destinations also need preview and confirmation; clearing a selection never bypasses required relocation.
- Bank trading stacks give/receive cards, defaults to the best core-derived 4:1/3:1/2:1 payment rate, permits eligible rate alternatives, and shows exact payment/receipt and resulting balances before confirmation. Draft choices survive sheet dismissal; ending a turn warns only if a pending trade would be discarded.
- Port access derives from coastal buildings. Owned-port chips, all-nine-port directory, port details, and owned-port payment shortcuts retain their existing behavior. Each directory control is at least 48 pixels high. Placement picking takes priority over port inspection.
- The primary button follows the phase: Roll, Confirm Placement, End Turn, or Results. Honey limestone marks roll/confirmation; dark green basalt gives ordinary turn completion a calmer treatment. A missing target disables confirmation. A rapid second primary tap cannot end the turn immediately after a build.
- Tapping a tile opens production number/probability, robber status, and adjacent-building details. Help → tile list provides keyboard access. Required next actions take priority in the history/context control; live notices announce confirmed feedback.
- Results retain the original victory emblem, winner, settlement/city score breakdown, final-board inspection, and return to menu.
- Animation never gates a command or changes state. Reduced motion removes travel and victory sparkles and keeps deltas stationary. Sheet entrance is a short opacity fade so drawing and semantic hit regions remain aligned.

## Installation and recovery

The menu has exactly Play and Tutorial, using honey limestone and green basalt respectively. Play resumes an unfinished save; Tutorial starts a fresh guided opening and asks before replacing any saved match, including a guided one. Play also resumes guided progress without restarting lessons. Both new-entry paths ask for a name and create four seats. Replacement confirmation precedes name entry; canceling either leaves the prior save intact. Blank names default to «بازیکن», names are limited to 24 characters with whitespace/control normalization, and runtime markup escapes them. Names persist with the existing match snapshot; Play resume never asks again. Installation guidance appears in a dismissible app modal once on non-standalone startup, never as an extra menu button. Help opens that app workspace and saves/returns to the menu. A downloaded release opens a dedicated update confirmation once, in the menu or during gameplay after the current sheet closes. Later dismissal keeps the update reachable through Help without adding a third menu action. All new surfaces use the existing Phaser Graphics/Text renderer, native modal, and semantic controls. Browser installation prompts require an explicit tap; iPhone users receive Share → Add to Home Screen instructions. Updates download in the background. Confirmation saves the current match, activates the waiting worker, and reloads into the new release; an unavailable save blocks updates during unfinished matches. Another open page offers its own confirmation and never reloads automatically. `pwa/updateFlow.ts` owns prompt timing and save-before-update behavior; platform checks run on launch/resume/reconnection and every five minutes while visible and online. Resuming restores confirmed state and narrator memory without historical animation or unconfirmed drafts. Storage errors remain visible without blocking play. See [PWA_RELEASE.md](PWA_RELEASE.md).

## Guided play

The menu's **سفر با آناهیتا** choices start a guided single-player match with three bots. `tutorial/director.ts` observes confirmed transitions and current UI context; `tutorial/lessons.fa.ts` contains the Persian narrative and expression choices. New matches ask for a name before creating the board or starting Anahita’s welcome; saved games keep their existing name. The native narrator modal places a large transparent portrait of the complete supplied figure on its own stage above a carved-stone dialogue panel. The panel lip covers the bottom 32 pixels of the portrait, attaching the silhouette to the box. A separate Phaser layer keeps the portrait outside the scrolling text mask and behind the panel, with restrained amber light, a warm stone rim, and a turquoise rosette detail. The portrait is up to 420 pixels high, sized from the viewport; the panel is capped at 50dvh with independently scrolling text and a fixed action footer. Short landscape layouts reduce the portrait and allow a taller panel. Continue receives focus and text scroll resets for each new lesson. The modal returns to the interrupted workspace or selected placement after acknowledgement. Closing or pausing stops automatic guidance; Help → **دفتر سفر آناهیتا** resumes it or replays any lesson. The journal distinguishes reviewed conversations from confirmed actions practiced while guidance is enabled. The context strip keeps phase-aware objectives visible between conversations and opens the journal; history remains accessible through Help. Full-resolution WebP expressions load on demand, then prefetch only the next queued expression, with a rosette placeholder while loading; original PNG masters live outside runtime assets. All text remains runtime Persian and all visible output remains in Phaser. See [TUTORIAL_DESIGN.md](TUTORIAL_DESIGN.md).

## Typography and verification

Domestic negotiation pins the human's complete resource hand in a `SheetContent.context` slot between the heading and independently scrolling body. `InterfaceScene` paints this context on the modal layer outside the body mask, as it does the footer. The resource strip shows only the human’s resource names, icons, and counts; it has no building-goal controls or planning guidance. Payment warnings and final balance review stay specific to the proposed exchange, without exposing opponent hands. See [DOMESTIC_TRADING.md](DOMESTIC_TRADING.md).

Self-hosted Vazirmatn Regular (400), with Tahoma/Arial fallbacks, supplies both semantic measurements and Phaser Text via `UI_FONT_FAMILY`. `index.html` preloads it and `loadUiFont()` completes before Phaser starts. No extra font weights are shipped. `rendering/sharpText.ts` rasterizes interface, board, port, and feedback labels at the canvas density: font sizes, metrics, padding, and strokes are multiplied, then the Text object is inverse-scaled to retain CSS dimensions. Keep `Text.resolution` at 1: the installed Phaser 4.0.0 RTL path uses backing-canvas width in a scaled context when resolution exceeds 1, shifting or clipping Persian text. Increasing raster font size avoids that bug without editing Phaser. Font bounds are measured from the loaded Persian font and `textGeometry.ts` aligns each label to its browser baseline, accounting for rounding at raster density. Explicit font metrics and padding refresh when responsive text size or density changes; ellipsis and crop calculations convert between raster and CSS units. Stone controls/cards use dark ink and their own muted/warning/rate colors; basalt panels keep warm light text. The measured flat-face text pairs range from 4.52:1 (shortage text) to 12.02:1 (panel body text). Disabled stone controls flatten and mute the material while keeping label opacity, rather than fading small text.

The user performs interactive/device testing and CI. Agent verification uses low-cost TypeScript checks, scoped lint/format checks, and focused pure layout/unit tests in Node. Leave full game verification, production builds, and CI runs to the user unless explicitly requested. Do not launch a browser without an explicit request. Tests cover density budgets, physical camera projection/culling, CSS input alignment at integer/fractional densities, raster text scaling, baseline/reading-edge alignment, inline font-size alignment, ellipsis, target preview/confirmation, robber relocation, inspection IDs, and coordinate agreement between inset-camera input and resource-flight anchors; they do not claim to validate CSS viewport behavior, visual appearance, or native-modal behavior on devices.

## Beginner clarity

The menu Tutorial opens a disposable four-step exercise rather than replacing the saved match. Its persistent step strip and primary action lead to a real roll/production, sample road, bank trade for missing wool, and settlement/score change. Staged conditions and idle opponents are disclosed. Completion/exit returns to the menu; the saved match is preserved. See [TUTORIAL_DESIGN.md](TUTORIAL_DESIGN.md).

The construction dock shows the count of currently actionable piece types. Action-phase context reports available builds, bank/negotiation availability, and end-turn. The context supports two lines within its existing 48-pixel row. Build cards have explicit resource, cost, current hand, and shortage columns, a purpose/points line, and separate legal-location or phase/turn explanations. They remain inspectable during bot turns using only the human hand; mutation remains guarded. Bank and domestic composition/final review show each build’s shortages before and after payment/receipt and whether a legal location exists, without selecting a strategy.

Settlement/city icons share their actual board contours. The city has a broad L-shaped compound with a deep open quarter; the compact settlement remains filled in that region. Silhouette carries the distinction in grayscale at mobile sizes.
